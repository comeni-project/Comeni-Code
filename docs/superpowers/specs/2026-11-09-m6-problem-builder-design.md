# M6.8b — The problem builder

**Status: draft 2026-11-09.** Part of M6.8 (#335), issue #424. Designed with the operator on
2026-11-09 from the boards at https://claude.ai/artifact/XBAFuB5b2X7WKG8SdAgx3i (`WorkbenchProblem`,
`WorkbenchProblemNew`, `ReviewProblem`; generated by `.design/build_pages.mjs`'s `benchProblem`,
`benchProblemNew` and `reviewProblem`). Builds on M6.7 (`2026-11-07-m6-problems-design.md`:
`problem.yaml`, the kits, `PUT`/`DELETE /problem`, the review key) and M6.8a
(`2026-11-09-m6-learner-problem-design.md`: `Problem.tsx`, `NodeProblemOut`).

## What it does

An author builds a node's problem in the workbench's **Problem** tab: the words, the kit and its
params, the sample, hints, which of the kit's mistakes point to which misconception callout, and
the rationale, as a form over `problem.yaml`, or the file itself. **Save** sends the file; the server's
20-seed self-test accepts or refuses it. A reviewer sees the problem in Review, drawn as the page
will draw it, with what only a reviewer judges. Authors' own mistakes and kits stay deferred (#425).

**In:** the Problem tab; `GET /api/studio/problem-kits`; the kits' descriptions and examples; the
YAML document module made general; problems that name their field; Review's problem key; the
Content row's link to the tab.

**Out:** new kits (each a reviewed change to `code-problems`); mistakes defined by authors (#425);
a preview of unsaved changes (only the server computes a sample).

## M6PB.1 The tab

`/studio/drafts/:id?tab=problem`, between Links and Settings (`TABS` in `WorkbenchPage.tsx`).
Content's problem row (today *built in M6.8*) becomes *Open in the Problem tab*. Every role that may
edit the draft may use it; a submitted draft shows the tab read-only, as the others do.

- **No problem yet** (`WorkbenchProblemNew`): one card per kit with its rung, one line on what the
  learner returns, and its sample dataset and output; *Start from this kit*.
- **A problem** (`WorkbenchProblem`): the form, *Edit as YAML*, *Remove the problem*, *Save problem*.
- The right panel: Preview (the problem from the last saved revision, through `Problem` with no live
  part, and *Self-test · passed* when it saved) and Checks, as the other tabs.

## M6PB.2 The file is a YAML document, edited in place

The form never writes a new file: it opens the text with the YAML document module the composer uses
(`figures/document.ts`, M6.5 CO.3: comments, key order, quoting and untouched lines kept; numbers in
plain decimal; strings quoted when their plain form reads two ways) and changes the nodes an edit
touches. The module moves to `src/yaml/document.ts` (`FigureDocument` renamed `YamlDocument`;
`openFile`, `setAt`, `insertAt`, `removeAt`, `moveAt`, `lineOf`; it still reads `TWO_READINGS` and
`CHARACTERS` from `figures/schemas`); the composer imports it from there.

- **One change in behaviour, for both:** a string written as a block scalar (`|` or `>`) stays one
  when edited, rather than becoming a double-quoted line. Today `scalarFor` keeps only the quote
  style, so editing `statement: |` would rewrite it. A composer test pins that its files are
  unchanged by this. *My call, after the builder check.*

- **Edit as YAML** shows the whole text in a monospace area; leaving it re-opens the document, and
  the form shows it again if it can hold it.
- **What the form can hold** (`problems/formable.ts`, new; it reuses the general half of the
  composer's rule: parses, no alias, no two-readings form, no tag, lines kept): a mapping of only the
  file's keys, a kit the endpoint knows, `params` and `sample.params` mappings, `hints` a list of
  text, `mistakes` a mapping of text. Anything else stays in Edit as YAML with the line that says
  why. Within those shapes, a wrong count of hints or a mistake the kit doesn't declare is a finding
  under its field, not a reason to leave the form. *My call, after the builder check.*
- **Start from this kit** writes a first file in the browser from the kit's example (M6PB.4), with
  empty words; it is unsaved until Save.

## M6PB.3 The form

As the board draws it, each field one key of the file:

| Field | Key | Control |
|---|---|---|
| Title | `title` | input |
| Rung | `rung` | select 1–4, the kit's rung first, words as M6.8a's (*read it off the file* …) |
| Statement | `statement` | Markdown area (formulas allowed) |
| Given, Return | `given`, `return` | one-line inputs |
| Kit | `kit` | select of the kits; changing it replaces `params`, `sample` and `mistakes` with the new kit's example after a confirm in the page |
| Params | `params.*` | one input per property of the kit's schema, its bounds as the hint: integer, number, a range as two inputs. A small `ParamsForm` of its own, for a flat object of numbers; the composer's `SchemaForm`, tied to figures' components and `data`, is not touched |
| Sample | `sample.seed`, `sample.params.*` | seed, then the same inputs |
| Hints | `hints` | 1–3 inputs, *+ Hint*, remove |
| Mistakes | `mistakes.<name>` | one row per mistake the kit declares: its name, its one line, a select of the body's misconception callouts' titles or *the checker's sentence only* (the key removed). No misconception callouts: the row says *Add a misconception callout in Content* |
| Rationale | `rationale` | area |

**Checked in the browser as you type** (no request): the params and the sample's params against the
kit's schema, with the validator the composer uses (`figures/validate.ts`, the twin of
`code_figures.schema`, its root path `params` or `sample.params`); title, statement, given, return
and rationale not empty; 1–3 hints; a mistake mapped only to a callout the draft's body has now (the
form reads the draft as saved, so a callout renamed in Content is caught here). A finding shows under
its field, as the composer's do. A kit's cross-param `rules` and the self-test (CS1102–CS1105,
CS1111) run only on the server.

## M6PB.4 What the browser knows about the kits

`GET /api/studio/problem-kits` (authors and above), fetched once while the tab shows
(`staleTime: Infinity`), from `code_problems.registry`:

`[{name, rung, about, schema, mistakes: [{name, says}], example: {params, sample: {seed, params}}, sample_dataset, sample_output}]`

- `about` (one line) and `says` (one line per mistake) are new on each `Kit`; `example` is new too:
  params that pass its self-test and a sample under 2,000 bytes. A test runs each kit's example
  through `self_test` and asserts every declared mistake has a `says`.
- `sample_dataset` and `sample_output` are the example's sample, computed, so the new-problem cards
  show what the kit makes.
- *Rejected:* a generated file committed to the web app (as `figures/schemas.ts`): one more file that
  can drift from the kits, for a screen that is online anyway.

## M6PB.5 Save, refusal, remove

- **Save problem** sends `PUT /api/studio/drafts/{id}/problem {revision, text}` with the document
  written back, one request. It is disabled while the form has a browser finding or a save is in
  flight; it reads *Checking with 20 seeds…* while sent.
- **Accepted**: the draft as answered (one GET saved, as `useDraftEdit` does), the preview redrawn,
  *Self-test · passed*.
- **Refused** (CA0208): each problem whose `field` names a key of the file (`params.k`,
  `sample.params`, `mistakes.duplicates`, `hints[0]`) shows under that field; the rest (a seed's
  failure, `kit`) above the form. Nothing is lost: the text stays as edited. The refusal's sentence
  names the problem (today it says *The figure's file would not validate*).
- **Problems name their field** (`code-schema`): today `problem_file.py` sets no `field`, folds a
  self-test finding's path into its message and gives CS1110 the `mistakes` key's line. Each problem
  now carries `field`: the self-test finding's path (`params.k`, `sample.params`, `mistakes.<name>`,
  `kit`), CS1110 and CS1111 their key (`mistakes.<name>`, `hints[i]`), CS1107 its key. CS1104 comes
  once per mistake, naming its first failing seed, not once per seed. The messages are otherwise as
  pinned. *My call, after the builder check: matching by line or parsing messages is fragile.*
- **Stale** (CA0203, another save first): the tab's usual sentence and *Reload*.
- **Leaving with unsaved changes** warns: leaving the draft through the composer's
  `useLeaveGuard` (its sentence made general), and **switching tab** through an in-page confirm on
  the tab bar (*Save the problem first? Save · Discard · Stay*), since `useLeaveGuard` watches only
  the path and `?tab=` keeps it. The unsaved text lives in the tab; discarded when you leave it.
  *My call, after the builder check.*
- **Remove the problem**: an inline confirm (*Remove the problem and its block? This can't be
  undone in the draft.*), then `DELETE …/problem?revision=`; the tab returns to the kit cards.

## M6PB.6 Review's problem key

`ReviewContentOut.problem` (M6PR.6) already carries the file and what the page shows; Review's block
panel draws it, as `ReviewProblem` does:

- the problem through `Problem` with no live part;
- **What the learner doesn't see until they answer**: the rationale, each mistake and the callout it
  names (or *the checker's sentence only*), the kit and its params, *Self-test · passed on the
  sample and seeds 0–19* (a submitted draft's problem has passed: a save refuses one that does not);
- **problem.yaml**: the file, monospace, open;
- **Changes**: the file before and after, as a line diff (the panel's word diff over lines).

`NodeProblemOut` gains `rationale` and `mistakes` (`[{name, callout}]`) for this; the learner's
`LearnerProblemOut` does not.

## M6PB.7 Done when

0. Each CS11xx problem from a problem file carries its `field`; CS1104 once per mistake.
1. On a draft of a node with no problem, an author starts from `de-bruijn-edges`, writes the words,
   maps `duplicates` to a misconception callout, saves, and the preview draws it; the saved file keeps
   every line the author did not touch (a test edits one param and compares the rest).
2. A param out of bounds is flagged under its field before any request; a self-test failure (a
   mapped mistake not caught) comes back under `mistakes.<name>`.
3. Edit as YAML and back keeps the form and the file in step; a file that cannot be a form stays in
   Edit as YAML with its reason.
4. Remove the problem empties the tab and removes the block.
5. A reviewer opens the problem key and sees the drawn problem, what the learner doesn't see, and the
   file; Changes shows the file's diff.
6. Walked on the Compose stack at 1680 light and dark, against the three boards.

## Decisions, and the alternatives rejected

- **The workbench's tab** (board). Rejected: a page of its own like the composer; one problem per
  node fits a tab, as the exam pool does.
- **The YAML document edited in place** (as figures). Rejected: a canonical writer (M6.7 already
  kept files as written).
- **An explicit Save.** Rejected: save on leaving the tab, as other tabs do: a save here can take
  seconds and be refused, and must not happen by surprise.
- **Kits served by an endpoint.** Rejected: a generated, committed file.
- **Only the server runs the self-test.** Rejected: a TypeScript twin of the kits (M6.7 and M6.8a).
- **No preview of unsaved changes.** Only the server computes a sample.
