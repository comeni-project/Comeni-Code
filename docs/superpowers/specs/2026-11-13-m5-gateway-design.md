# M5.1 — The gateway and the AI settings

**Status: implemented; reviewed 2026-11-15. The operator's real ChatGPT sign-in (M5G.9.5)
and publication remain.** Part of M5 (#445), issue #446. Designed with the operator on
2026-11-13, from Labs' way of connecting models (read at `73f0052`, not imported: its settings
spec `docs/superpowers/specs/2026-10-01-settings-design.md` §3, §6, §8, and
`packages/comeni-ai`) and the boards at https://claude.ai/artifact/5zvkHY3awfkW9CCimEn1GS
(`AISettings`, `AISignIn`, `AIUsageM5`, generated by `.design/build_pages.mjs`).

## What it does

Code gets one door to models, `code_api.ai`, and a Studio page where an operator decides what is
behind it. **Connections** say where models come from: a ChatGPT plan signed in from the page, a
self-hosted server (Ollama, vLLM), a hosted provider with a key, or `.env`. **Each declared call
site** gets a model (or *same as default*), a cap and call settings. **Every call is recorded**, and
the Usage page shows what was used. With no connection nothing calls a model and every page still
works. No call site drafts or scores anything yet: that is M5.2 onward.

**In:** `code_api/ai/` (the gateway, call sites, connections, the ChatGPT sign-in, the call record,
the Studio routes); the AI page (`/studio/ai`, Models and Usage tabs); `CODE_AI_*` and
`CODE_SETTINGS_KEY`; LiteLLM as a dependency of `apps/api`; the AI line on the health page; codes
CA0400–CA0499.

**Out, and where it goes:** what each call site sends and does with a reply (M5.2–M5.5); scores and
the judge (M5.3, #451); caps in money and per person (later, when a key-billed site needs one);
caching; the M7 call sites (connecting text, request grouping, skeleton drafting), listed greyed.

## M5G.1 One door: LiteLLM in process

`code_api.ai.gateway.call(site, messages, *, by, reply=None, draft=None) -> Reply` is the only
function that reaches a model. It resolves the site's connection and model (M5G.3), checks its cap
(M5G.5), calls `litellm.completion`, records the call (M5G.6) and returns a `Reply`: `text`, the
parsed `value` when a Pydantic `reply` model was given (checked, never repaired: an invalid reply is
a refusal, as Labs' client does), and the call's id. A failure is a `Refused(code, sentence)`, never
an exception the caller must know about.

- **LiteLLM as a library, not a proxy container** (Labs' choice). R1's "one LiteLLM gateway" is read
  as one module every call passes through; Code records usage and enforces caps itself, so the
  proxy's own database, keys and UI would duplicate what this page does. LiteLLM is pinned to an
  exact version in `apps/api/pyproject.toml` (1.105.1, as Labs).
- **Synchronous.** A caller decides where a call runs; M5.2 runs drafting in Celery. *Test* (M5G.3)
  runs in the request with a 20-second timeout.
- **Tests never call a provider:** the gateway calls LiteLLM through one transport function, which
  tests replace with a fake (LiteLLM's `mock_response` does not isolate a `chatgpt/` model: the
  provider is resolved, and its token read, before the mock is checked); a guard test fails if a
  test reaches the network through the gateway.
- **LiteLLM never reads the host's environment for a call:** the gateway always passes `api_key`
  and `api_base` itself. LiteLLM fills a `None` key from the host (`api_key or …
  get_secret("OPENAI_API_KEY")`), so a hosted connection without a key is refused before LiteLLM
  (CA0400), and any other route without one is given the placeholder `none` (a ChatGPT plan, which
  answers by its token, takes no key); tests pin both. *(Corrected during the build: `None` was not
  enough.)* *My call, after the builder check: settings come
  only from `CODE_*` (CLAUDE.md), and LiteLLM would otherwise read `<PROVIDER>_API_KEY`.*
- **Only `code_api.ai` imports `litellm`**, checked by a repository test as `test_app_dependencies`
  checks imports today.

## M5G.2 The call sites: a fixed list

`code_api/ai/sites.py` declares every call site once: its key, its label, who calls it, what it does
when refused (its words for the page), its default cap, and the milestone that wires it. The list
is invariant 7's: goal suggestions, page drafting, figure data and problems, connecting text,
request grouping, assistant chats, skeleton drafting, resource suggestion, block evaluation; plus
**default**, which the others may follow. Adding a site is a reviewed code change. The M7 sites are
listed and greyed (*arrive with their screens*). A test fails if a site exists in code and not on
the page, or the other way.

## M5G.3 Connections

A **connection** is a row: a name, a **kind** (`chatgpt`, `self-hosted`, `hosted`), an endpoint
(self-hosted), a key (hosted, encrypted), and the time it was last tested with the outcome.

- **Test** sends one short call (`say ok`) through the connection's first model and records it.
  Self-hosted: the model list comes from `{endpoint}/v1/models` (Ollama and OpenAI-style servers);
  hosted: models are typed as `provider/model`, checked for that form (CA0401).
- **Keys** are encrypted at rest with Fernet, keyed by `CODE_SETTINGS_KEY`. Without it, adding a key
  is refused with a sentence that names the variable (CA0402). No response ever carries a key: it
  reads back as set, with its last four characters. The value is held in a type that prints hidden.
- **`.env` locks.** `CODE_AI_MODEL`, `CODE_AI_API_KEY` and `CODE_AI_BASE_URL` appear as a connection
  named *From .env*, read-only on the page, and its model is the default's, locked. An empty variable
  is unset. So an operator's deploy files stay the truth, as in Labs (§3: a lock, not a seed).
- **No connection, no AI.** With none, every site resolves to *no model*; `call` answers
  `Refused(CA0400)` at once and records nothing. The health page says *AI: not configured*.

## M5G.4 The ChatGPT plan: signed in from the page

LiteLLM's `chatgpt/` provider answers through a ChatGPT plan that includes Codex, with no key; calls
count against the plan's limits. Labs signs in from a command. Here the page does it. **One ChatGPT
connection per installation**: LiteLLM keeps one `auth.json` per folder, and the folder is a
process-wide variable.

1. *Sign in with ChatGPT* posts `…/ai/chatgpt/sign-in`: the API requests a device code through
   LiteLLM's `Authenticator._request_device_code` (which answers `device_auth_id`, `user_code` and
   `interval`) and keeps the attempt in Redis for 15 minutes. It answers the code and the link
   (LiteLLM's constant `CHATGPT_DEVICE_VERIFY_URL`). The page shows them, with *Device codes are a
   common phishing target. Never share this code.*
2. **The page drives the wait**: every 5 seconds it asks `GET …/chatgpt/sign-in`, and each ask makes
   **one** poll of the device-token URL (LiteLLM's constant), never LiteLLM's blocking loop, so no
   worker slot is held for 15 minutes. While the code is not approved the poll answers *waiting*
   (the provider cannot tell *not yet* from *declined*); after 15 minutes the attempt ends,
   CA0403.
3. Approved: the code is exchanged for tokens (`_exchange_code_for_tokens`), the record built
   (`_build_auth_record`) and written **by Code, atomically** (a temporary file renamed), under a
   Redis lock; the connection is added (or renewed) and tested.

**The gateway owns the token, so LiteLLM never starts a sign-in inside a call.** Before any
`chatgpt/` call the gateway reads `auth.json`: no token, `Refused(CA0403)` at once, without calling
LiteLLM. An expired access token is refreshed by the gateway (the refresh request made by Code with
LiteLLM's token URL and client id, since LiteLLM's `_refresh_tokens` writes the file itself, in
place; then the atomic write) under the same Redis lock, so `api` and `worker` never refresh at once; a refresh that fails
marks the connection *sign-in ran out* and refuses CA0403. LiteLLM then always finds a fresh token
and never reaches its own device-code login or its cooldown wait. *My calls, after the builder
check: left alone, a missing token made LiteLLM block a call for up to 20 minutes.*

**What the card shows:** *Signed in* with the last call that answered through it, or *Sign-in ran
out* once a refresh failed, with *Sign in again*. Not the access token's expiry: LiteLLM refreshes
that by itself, so it says nothing about the sign-in. *(The board's "8 days left" becomes "last
answered 2 min ago".)*

- **This drives LiteLLM's private methods and constants** (`_request_device_code`,
  `_exchange_code_for_tokens`, `_build_auth_record`, `CHATGPT_DEVICE_VERIFY_URL`,
  `CHATGPT_DEVICE_TOKEN_URL`, `CHATGPT_OAUTH_TOKEN_URL`, `CHATGPT_CLIENT_ID`), which any release could change. Hence the exact pin, and a test that
  fails when one is gone or changes its shape, so an upgrade is a reviewed change. If they go, the
  card falls back to Labs' command.
- **Where the token lives:** `CODE_AI_CHATGPT_DIR`, read by `env.py`, which sets LiteLLM's
  `CHATGPT_TOKEN_DIR` from it at start (the one place Code writes a library's variable, said in a
  comment). In Compose, a named volume `ai-chatgpt` shared by `api` and `worker` at
  `/var/lib/code/chatgpt`, which `Dockerfile.api` creates owned by the `code` user (uid 10001, no
  home, so LiteLLM's default folder cannot be made). `.env.example` sets `.run/chatgpt` for native
  development; tests use a temporary folder. Empty: the ChatGPT kind is greyed, *needs
  CODE_AI_CHATGPT_DIR*. The token never reaches the browser.

## M5G.5 A model, a cap and call settings per site

A **site setting** row per site: `model` (a connection and a model, or *same as default*), `cap`
(calls a day; empty means the site's default), and call settings (temperature, reasoning effort,
timeout; empty means the installation's). Choosing another model clears its call settings, since a
setting one model takes another may refuse (Labs). The **default** site has no *same as*; a site
whose connection is removed resolves to *no model* with a sentence (*its connection was removed*),
never an exception.

**Caps count calls** in the current day (UTC), from the call records: a ChatGPT plan has no price
per call. At the cap, `call` answers `Refused(CA0404, "<site> reached its cap of N calls today")`
and records the refusal. Money caps wait for a key-billed site that needs one.

## M5G.6 The call record

`AICall` (append-only): site, the person (`null` for a learner's call: no identity), connection
name, model, prompt id (the caller's), tokens in and out, cost when LiteLLM reports one (`null` for
a plan or a self-hosted server), duration, outcome (`answered`, `refused`, `capped`, `failed`), the
refusal's code, the draft it served (by public id, set by M5.2), and when. **No prompt or reply text
is kept**: a drafted block is its own record, and a learner's goal is not stored (invariant 9's
spirit, and size). Provenance (M5.2) points at the call's id.

## M5G.7 The AI page (`/studio/ai`, operators)

`STUDIO_PAGES` gains *AI* for operators. Two tabs, as the boards draw them (the board's Budgets tab
is dropped: caps live on Models):

- **Models:** Connections (each with its kind, where it points, its status from the last test,
  *Test*, *Edit*, *Remove*; *From .env* locked) and *Add a connection* (Self-hosted · A hosted
  provider · ChatGPT plan); then *Where Code calls a model*, one row per site: who calls it, the model
  menu (*same as default* or every model on every connection, *ChatGPT plan · gpt-6.1-sol*), what it
  does when refused, the cap, and *Call settings*. Each change saves on its own, applies to the next
  call, no restart. A locked value is greyed and says *set in .env*.
- **Usage:** today / this week / this month: calls, tokens, cost where billed, calls on a plan,
  refusals; by site and by person (learners together); the recent calls with their outcome.

Routes under `/api/studio/ai/` (operators; the usage read is operators too): `GET settings`,
`POST/PUT/DELETE connections[/{id}]`, `POST connections/{id}/test`, `PUT sites/{key}`,
`POST/GET chatgpt/sign-in`, `GET usage?range=`. Each answer is the page's state, so a save needs no
second read.

## M5G.8 Codes (CA0400–CA0499, new band: AI)

CA0400 no model for this site · CA0401 a model not in `provider/model` form · CA0402 a key without
`CODE_SETTINGS_KEY` · CA0403 no ChatGPT sign-in: never made, not approved within 15 minutes, or its
refresh failed · CA0404 a site at its cap ·
CA0405 the provider refused the call (its words kept) · CA0406 a reply that is not the shape asked
for · CA0407 a locked setting. Each in `diagnostics.yml` with `explain` and a test.

## M5G.9 Done when

1. With no connection, `call` refuses CA0400 and every page works; the health page says so.
2. A self-hosted connection (a stub server in tests; Ollama in the walk) is added, tested, its models
   listed, chosen for a site; a call through it is recorded with its tokens and duration.
3. A hosted key is stored encrypted, never returned, refused without `CODE_SETTINGS_KEY`; `.env`'s
   model shows as *From .env*, locked.
4. A site at its cap refuses CA0404 and the refusal is recorded; Usage shows the counts.
5. The ChatGPT sign-in: the code and link shown, approval polled one ask at a time, the token written
   atomically, the connection added and tested (walked by the operator with a real plan; the steps
   unit-tested with HTTP faked). A missing token refuses CA0403 without calling LiteLLM; a failed
   refresh marks *Sign-in ran out*. The private-method test passes on the pinned version.
6. The AI page matches the boards, walked at 1440 light and dark.

## Decisions, and the alternatives rejected

- **LiteLLM in process, in one module.** Rejected: the LiteLLM proxy as a Compose service, which
  duplicates the page's records and adds a database and keys to run.
- **Caps in calls.** Rejected: caps in money now: a plan or a self-hosted server has no price.
- **No prompt or reply text in the record.** Rejected: storing it for debugging, which keeps
  learners' goals and doubles every draft.
- **The ChatGPT sign-in in the page, through LiteLLM's private methods, pinned and guarded; the
  page drives the wait, and the gateway owns the token.** Rejected: Labs' `docker exec` command,
  which needs a shell on the server; a Celery task in LiteLLM's blocking loop, which holds a worker
  for 15 minutes; leaving the token to LiteLLM, which signs in inside a call.
- **Settings in their own tables**, not a generic key-value settings store as Labs': Code has one
  page of them and typed rows are simpler to check.
