# M4.3 — Accounts, invites and roles: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this
> plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The team signs up by invite only, by password or GitHub, with a ranked role; Studio
routes are gated by role; learner routes still need no account. No screens: the API M4.8 calls.

**Architecture:** django-allauth in headless browser mode at `/_allauth/browser/v1/`, its sign-up
gated by an adapter that requires a pending invite in the session. `accounts.User` keyed by email
and a `public_id` UUID, with a `role`. Our Ninja routes: `/api/me`, `/api/invites/…`,
`/api/team/…`, gated by one auth class, `studio(min_role)`.

**Tech stack:** Python 3.14, Django 6.1, Django Ninja, django-allauth 65.19, pytest, mypy strict.
The web app changes only its dev proxy and its generated `schema.ts`.

**Spec:** `docs/superpowers/specs/2026-10-05-m4-accounts-design.md` (M4A.1–M4A.5), issue #121.

## Global constraints

- **Settings come only from `CODE_*` variables** in `code_api/config/env.py`; every new one is in
  `.env.example`.
- **Learner routes keep no auth**, and their responses do not change.
- **Error bodies are `Message(detail, code)`**, as the content API's are; new codes go in
  `diagnostics.yml` in a new band `CA0100–CA0199 · accounts`, each named by a test, and the
  reference page is regenerated.
- **Tests never reach GitHub**: allauth's GitHub endpoints are mocked.
- Postgres and Redis run under podman (`code-dev-postgres` :5433, `code-dev-redis` :6380). Never run
  the API tests while a reviewer runs them.
- Web commands run in `node:24-alpine` under podman, one `npm` command per run:
  `podman run --rm -u "$(id -u):$(id -g)" -e HOME=/tmp -v "$PWD":/repo:Z -w /repo/apps/web
  docker.io/library/node:24-alpine npm <command>`.
- After any API change: `export_openapi_schema … --output apps/api/openapi.json`, then
  `npm run api-types`.

## Review focus

- Task 4's gate: no path creates a user without a pending invite (password, GitHub, a replayed or
  expired token, a token for another email).
- Task 3's `studio` class: 401 vs 403, CSRF on writes, inactive users.
- The fresh-reviewer checkpoint is after Task 4; the final review is over the whole branch.

### Task 4: Invites and password sign-up (M4A.2)

**Files:**
- Create: `code_api/accounts/invites.py` (`Invite`, token minting and hashing, pending, accept),
  `code_api/accounts/adapter.py` (allauth `AccountAdapter.is_open_for_signup` and `save_user`),
  `code_api/accounts/management/commands/invite_operator.py`; the migration.
- Modify: `accounts/models.py` (the `Invite` model), `accounts/api.py` (`/api/team/invites`: POST,
  GET, DELETE under `studio(Role.OPERATOR)`; `/api/invites/{token}` GET and `/accept` POST with no
  auth), `settings.py` (`ACCOUNT_ADAPTER`, `ACCOUNT_EMAIL_VERIFICATION = "none"`),
  `diagnostics.yml` (CA0103 unknown, CA0104 expired, CA0105 revoked, CA0106 used, CA0107 already
  a member).
- Tests: `apps/api/tests/test_invites.py`.

- [ ] **Step 1: Write the failing tests.**
  - An operator invites; `mail.outbox` holds one message with `<CODE_WEB_ORIGIN>/join/<token>`;
    the row stores `sha256(token)`, never the token.
  - Lookup: 404 `CA0103` unknown; 410 `CA0104`, `CA0105`, `CA0106` for expired, revoked, used.
  - A second invite to the same address revokes the first; inviting a member is 409 `CA0107`;
    an author or reviewer inviting is 403.
  - Accept then sign up by password through `/_allauth/browser/v1/auth/signup` (with CSRF): the
    user has the invite's role, the invite is used, the session is signed in.
  - Sign-up with no accepted invite is refused, and no user exists; with another email than the
    invite's, refused; with an expired invite accepted earlier, refused.
  - `invite_operator a@x.org` prints a link whose token looks up to an operator invite.
- [ ] **Step 2: Run them.** Expected: fail. **Watch the refusal tests fail** against an adapter
  that opens sign-up to all, before trusting them.
- [ ] **Step 3: Implement.** Use one transaction for the user, its role and the invite's
  acceptance.
- [ ] **Step 4: Run** `uv run pytest`, `uv run mypy`, `makemigrations --check`, regenerate the
  reference. Expected: pass.
- [ ] **Step 5: Commit** `feat(accounts): invites, and sign-up only through one — M4.3.4`.
- [ ] **Checkpoint:** a fresh reviewer over Tasks 1–4 against the spec. Fix what it finds (an issue
