# 2026-09-19 — M2 in parts

**Phase M2 (the weaver) starts.** M1 is done: nodes are files that validate, and the index serves
them ([the previous entry](2026-09-19-m1-part-6-command-and-api.md)). M2 turns goal ids into a
**route**, with a pure function in `code-weaver`, and it is split into four parts. **No weaver code
exists yet.** Next is the spec for part 1, which waits for the operator's approval before it gets a
plan.

The operator made every decision below; an agent proposed the parts and drafted.

## Decisions made, and why

1. **M2 builds W3.3's steps 2, 4, 5 and 6.** Walk back, remove what is known, order, explain.
   These are the pure steps: same graph, goals and known set, same route.
2. **Step 1, resolving a learner's words to goals with a model, is M5's**, where R4 already puts
   *goal suggestions … with a search fallback*. Until then a goal is a list of node ids, which the
   CLI and the API take directly. The weaver's input does not change when a model sits in front
   of it.
3. **Step 3, *any-of* choices, has no phase.** It is designed (W3.2) and refused by the validator
   until wired, and the Salmon fixtures needed none. It comes back as a part of its own when real
   content needs "one of these", most likely from the master's-class seeds. The other steps do not
   change when it does.
4. **"Known" is an input** in M2: a list of node ids. Stored learner evidence (T7) supplies it
   later.
5. **The fixtures' 17 stops are the reference route, not the Route board's 13.** The board was
   drawn on 2026-09-17 with *de Bruijn graphs* on the route; M1 part 4 took it off, by the need
   rule, and pinned 17 stops from no background. R4's *done when* carries a dated note saying so;
   the board is redrawn in M3's design round.
6. **The level span of the Salmon route is *First steps → Intermediate*.** *Salmon*, its hardest
   stop, is intermediate. The board's *First steps → Advanced* counted nodes attached below the
   route, which are not stops.
7. **Parts 1 and 2 are separate**, so the ordering rules get their own brainstorm before
   explanations are built on them.
8. **Out of scope:** connecting text (route introductions, bridges, why-for-your-goal; W3.4),
   routes as tracks (W3.5), and any page. Those are M3, M5 and M7.

## What is next — the M2 parts

In this order. The CLI and the API are ways to reach the function, so they come after it; the API
is last because it reads the index, not files.

| # | Part | Objective | Check |
|---|---|---|---|
| 1 | Walk back and order | A pure function from a graph and goal ids to an ordered route (W3.3 steps 2 and 5): follow *needs* recursively; order so each stop follows what it needs; ties by region, then the author's order; a *needs* cycle refused with a message naming it. The runtime purity guard runs a weave | The fixtures give exactly the 17 route stops in a pinned order; repeated runs are byte-identical; a cycle is refused |
| 2 | Why, known, and level span | Each stop's chain of *needs* reasons back to a goal (step 6); a known set removed with everything only it needed (step 4); the route's level span | *k-mers* is explained through *read mapping* and *Salmon*; marking *read mapping* known drops what only it needed; the span is *First steps → Intermediate*; every level changed gives the same route |
| 3 | The CLI | `code-weaver route <goal>… --root <folder> [--known …]`, reading files through `code-schema`, printing the route with its reasons | The Salmon route prints identically every run; exit codes follow `code-schema validate`'s |
| 4 | The API | An endpoint in `apps/api` that weaves from the index; `openapi.json` and `schema.ts` regenerated | It gives the CLI's route for the same goals; an unknown goal is 404, or 503 before any applied build |

M2 is done when R4's *done when* holds: the Salmon route matches the reference route, repeated
runs are byte-identical, a cycle is refused, and the same graph with every level changed gives the
same route. That is the checks for parts 1 and 2, reached through parts 3 and 4.

## Open questions

- **What the weaver takes as a graph**: `code-schema`'s own objects, or a smaller type of its
  own that both the files and the index can fill. Part 1 decides; the API in part 4 depends on it.
- **What "ties by region" means**: the order of `regions.yaml`, or something else. Part 1 decides.
- **The route's output format**, which "byte-identical" is measured on. Part 1 or 3 decides.

## Traps

- **`code-weaver` is pure** (`tests/guards`): no Django, no HTTP client, no model library. The
  endpoint in part 4 lives in `apps/api`, not in the package.
- **Tests never read the real content repository** (R1). Everything in M2 runs against
  `tests/fixtures/salmon/`.
- **The Route board shows 13 stops.** Do not test against it; the reference is M1P4.2's 17.
