# 2026-09-29 — M4 in parts

**Phase M4 (the Studio core) starts.** M3 is done and closed (#79). M4 turns Code from something
learners read into something the team writes: sign in with a role, draft a node, check it, review
it, land it on `comeni-code-content` through a pull request, and see the learner page change once
the worker picks up the merge. It is split into **nine parts**, back end first, screens last.
**No Studio code exists yet**: `User` is an empty subclass, there is no allauth, no draft, no
landing and no worker following the content repository. Next is the spec for part 1, which waits
for the operator's approval of this list.

The operator decided the questions below in a brainstorm and approved the four sections of parts;
an agent proposed them.

## Decisions made, and why

1. **The block document comes in M4, thin** (operator, after asking which is better long term).
   `body.md` stays Markdown on disk; the app reads it as typed blocks; only `text`, `try` and
   `callout` are wired, and `figure`, `math`, `image`, `example` and `problem` stay designed and
   refused by name until M6 — the pattern *helps* and *any-of* already follow. Why now: invariant 6
   and W5.1 need blocks, M5's assistant edits through block calls (W5.2), a Markdown-textarea
   workbench would be built twice, and migrating content only gets dearer once real content lands.
   It is one part, not a doubling, because `body.md` already splits into text and `try`.
   *Rejected:* keeping Markdown for M4 (the agent's first recommendation, on cost alone; it pays
   later with a second editor and a migration); the full block document (designing figure and
   problem shapes before M6 builds a component).
2. **Back end first, then the screens** (operator). The pipeline is built and proven through the
   API — the risky GitHub and worker end before any screen depends on it. *Rejected:* a thin
   slice end to end first (every step rebuilt later); one part per screen as in M3 (landing built
   late, inside its screen).
3. **Sign-in is email and password, and GitHub; invite-only** (operator). The team is on GitHub,
   and landing needs a GitHub side anyway. ORCID arrives with learners in M8, as one more allauth
   provider. *Rejected:* email only; all three now (an ORCID client registered before M4 can
   check).
4. **Studio lands as a GitHub App** (operator), installed on `comeni-code-content` only, with
   contents and pull-request write. Short-lived tokens; pull requests show as the app, so "not from
   Studio" is checkable, which is what #102 needs. *Rejected:* a machine account's long-lived
   token; landing as the signed-in operator (#102 could not tell Studio from a person).
5. **#101, a sign-in shared with Labs: not in M4, kept open** (operator). M4 builds Code's own
   accounts, keyed so Code could later be an OIDC provider or join an identity service without
   migrating users. *Rejected:* Code as a provider in M4; a separate identity service now.
6. **#102 is decided in M4.6's spec.** R1 already says pull requests from outside Studio need a
   maintainer's review; R8.9 only asks how, with one maintainer. The agent's proposal to argue
   there: a content-repository check that passes for the app's pull requests and requires a
   maintainer's approval for anyone else's, exempting the operator while they are the only one.
7. **Screens match the original boards as closely as possible** (operator), read from
   `.design/build_pages.mjs` as M3 part 5 did; what waits for the end of the MVP is content and
   finishing polish, not the boards' design. Anything a board draws that M4 does not build is
   absent, not faked.

M4 is done when R4's *done when* holds: one node goes draft → checked → approved → landed, and
learners see it after the worker picks up the merge; the landed node has a level, at least one
resource and an exam pool of at least four approved questions. That is part 9's walk, with parts
1–7 proven underneath it.

## Open questions

- **The directive syntax** — Markdoc as the markers are today, or MyST as R1 wrote. Part 1's spec.
- **Whether two authors may hold drafts of one node** at once, or a draft locks it. Part 4's spec.
- **How a draft relates to the index**, whose rows are disposable and named by id. Part 4's spec.
- **Webhook or polling** for the worker, and when a hosted stack gets the webhook. Part 7's spec.
- **Which node lands first for real** in part 9 — the operator's pick; one small real node is
  enough, since content work waits for the end of the MVP.

## Traps

- **The content repository's pin must move before the first landing.** Its CI validates with a
  pinned Comeni-Code commit; a node with blocks or an exam pool fails an older validator.
- **Tests never touch GitHub or the real content repository** (R1): a local bare remote and a fake
  of the GitHub API stand in, and part 9 is the one outward walk.
- **The published canvas does not open on this Claude account.** Parts 8 and 9 need it, or a link
  that opens, for the side-by-side check; until then, measures come from `.design/build_pages.mjs`.
- **Exam answers must never reach the browser**, unlike `try` answers; the check is a test, not a
  comment.
