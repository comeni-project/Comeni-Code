## Decisions made, and why

1. **The Route page carries no stored learner state.** Progress per line, *how many you already
   hold*, time left *for you*, milestones and *not yet reviewed* all need learner records (T7) or
   the Studio (M4). M3 draws the map, the selected-stop panel, the time and the level span, and
   **`known` comes from the URL**, exactly as the weaver already takes it — so the route really
   does shorten, and nothing is stored. *Rejected:* a small learner record now (it decides what
   evidence means before the tutor loop that defines it); placeholder numbers on the page (a
   screen that looks finished and reports nothing true).
2. **Resources and try questions enter in M3, read-only.** `resource` blocks (T4.1) and `try`
   with `hints` and `rationale` (T6.2) go through the schema, validator, loader, index, API and
   the page, with fixture nodes carrying them. **No authoring UI** — that is M4's workbench. This
   keeps R4's *done when* whole, at the price of content-core work inside a screens phase: M3
   shows no screen until part 3. *Rejected:* resources now and questions with the question
   builder; neither, which would leave the Node page beside its board without its *Learn it*
   section.
3. **The body stays Markdown in M3.** `body.md` is rendered as it is, styled in the identity.
   W5.1's block document arrives with M4's workbench, where the structure is needed to edit a node
   piece by piece — resources and questions are their own fields either way, so *Learn it* and the
   questions are structured while the prose is not. *Rejected:* blocks now (a schema round, a
   fixture rewrite and a renderer per kind, inside the phase whose point is the screens).
4. **Data before screens.** Parts 1 and 2 build what the pages read, so no page is ever built
   against a mock and then rewired.
5. **The app's spine arrives with the first screen** (part 3), not as a part of its own: a router,
   a top bar with search and fetching against the generated types are not worth a part unless
   something uses them.
6. **The First steps node page is its own part**, not a variant folded into part 5. T10.2 calls it
   an interface change — larger type, shorter pages, less density — and it is the one place the
   audience reaches the design.
7. **Out of scope:** Placement (L2), Home (L3), problems (L6), review (L7), knowledge (L9),
   explore (L12); accounts and stored progress (T7); *not yet reviewed* labels (M4); missing-node
   requests (M7); AI goal suggestions (M5); figures (M6); connecting text (W3.4).

## Open questions

- **How search ranks**, and whether it is a database query or a small pure function the API calls.
  Part 2 decides; part 3's Start page depends on it.
- **How a metro map is drawn**: lines from the route's regions, or something else, and what draws
  it — SVG by hand, or a layout library. Part 4 decides.
- **Whether `try` questions need a stored answer** to feed review (T7), or stay a page interaction
  in M3. Part 1 decides the schema; the page in part 5 decides the rest.
- **What the top bar's account menu shows** while there are no accounts. Part 3 decides.
- **Whether `IndexBuild` rows need pruning** (carried from M1 part 5).

## Traps

- **The Route board draws 13 stops and the fixtures give 17.** Do not test against the board
  before part 4 redraws it.
- **The pages are measured against the boards, not against taste.** `.design/*.dc.html` and
  `.design/tokens.json` are the reference, and the web app already reads the same tokens.
- **`apps/web` has no router yet, by design.** `App.tsx` switches on the path until part 3.
- **Tests never read the real content repository** (R1). Every fixture node M3 needs goes in
  `tests/fixtures/salmon/`.
- **No page may invent learner state.** If a number needs T7, it is not on the page in M3.
