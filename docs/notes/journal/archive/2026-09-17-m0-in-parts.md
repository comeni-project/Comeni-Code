## Decisions made, and why

1. **M0 is nine parts, each about one session.** The first proposal had five parts. The operator
   judged the API part and the web part too large, so each was split into three parts.
   **Rejected:** a separate CI part. Part 1 creates the CI workflow, and each later part adds its
   own job, so CI never checks code that doesn't exist yet.
2. **Merge the design PRs before any M0 branch.** M0 branches start from `main`.
   **Rejected:** stacking M0 on `docs/architecture-roadmap`, which would have put both design PRs
   into every M0 diff.
3. **The content repo's protection binds admins too.** It is a repository ruleset with no bypass.
   **Rejected:** allowing admins to bypass. The M0 check says a direct push to `main` is refused,
   and with a bypass the operator's own push would succeed.
4. **CI starts the Compose stack** in part 8 and checks the health page.
   **Rejected:** checking Compose only by hand, which would let the stack break unnoticed.

## What is next — the M0 parts

In this order. Part 1 goes first because it protects an invariant (the purity guard behind the
weaver's promise), settles the tooling every later part uses (R7), and needs no infrastructure.
Part 9 is independent and can run at any point, **with the operator's confirmation before each
change to GitHub settings.**

| # | Part | Objective | Check |
|---|---|---|---|
| 1 | Workspace, pure packages and purity guard | Python workspace; empty `code-schema` and `code-weaver`; purity guard; lint; CI on every PR | Tests and lint pass locally and in CI; a commit adding `import django` to a pure package turns CI red |
| 2 | Django project boots | `apps/api` in the workspace; settings from the environment; pytest-django against Postgres (a service container in CI) | `manage.py check` and migrations pass; a database test passes in CI |
| 3 | Ninja API and health route | The API under `/api/`; `/api/health` reports the database; OpenAPI schema generated | Tests: 200 when the database is up, 503 when it is down; the schema lists the route |
| 4 | Celery, beat and Redis | Celery app; beat runs a heartbeat task; health gains Redis and worker status | A CI test with a real worker and a Redis service; a stale heartbeat reads as down |
| 5 | Web toolchain | `apps/web` with Vite, React and TypeScript, plus vitest and a linter; `npm ci` in CI | Type check, vitest and `vite build` pass in CI |
| 6 | Identity tokens into Tailwind | The tokens in `.design/_identity.mjs` become the Tailwind theme, light and dark, from a single source | A test fails when the theme drifts; a screenshot sits next to the Identity board |
| 7 | Health page | TanStack Query reads `/api/health` through Vite's proxy; each state in words as well as colour | vitest covers the ok, down, loading and error states; screenshot |
| 8 | Compose | postgres, redis, api, worker, beat, web; **CI starts the stack** | After `docker compose up` the health page shows all healthy, in CI too |
| 9 | Content repo guardrails | CI stub, auto-merge, a no-bypass ruleset on `main` | A stub PR goes green; a direct push to `main` is refused, the operator's included |

M0 is done when R4's *done when* holds. That is the checks for parts 1, 8 and 9 together.
