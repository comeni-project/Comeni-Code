# 2026-09-18 — M1 in parts

**Phase M1 (Content core) starts.** M0 is done: the stack runs, CI gates both repositories, and
the three kinds of node link now each carry a reason
([the previous entry](2026-09-18-node-neighbours.md)). M1 turns a node into **files that validate
and load**, and it is split into six parts. **No content code exists yet.** Next is the spec for
part 1, which waits for the operator's approval before it gets a plan.

The operator made every decision below; an agent proposed the parts and drafted.

## Decisions made, and why

1. **M1 is six parts.** The first proposal was five, and the operator judged the first two too
   large: part 1 held every field of the format *and* the package *and* round-tripping, and it is
   the spec that all content is later written against. Splitting them costs nothing — the parts run
   in sequence either way — and it keeps each brainstorm short enough to be argued properly.
2. **`body.md` is opaque in M1.** The validator checks that it exists and parses as MyST, never
   what is inside it. The block document — figures, callouts, try-questions, the Rosalind problem
   (W5) — is a schema of its own and belongs with the parts that *make* those blocks, in M3.
   **Rejected:** validating blocks now, which roughly doubles part 1 and settles the shape of
   figures before anything draws one. M1's objective is the node as a file with links, not the node
   as a page.
3. **Per-node validation is not its own part.** With a schema library, *this field is missing*
   comes free from parsing, so it lives in the parts that define the fields. Part 3 keeps only the
   rules that need **the whole graph**, which is also where a validator can be genuinely wrong.
4. **Horizontal parts, not vertical slices.** An agent proposed a minimal node end-to-end first
   (schema → validate → fixture → index → API), then adding fields through the whole stack. Each
   part would end in something demonstrable, but it re-opens the schema and the index migration
   five times. **Rejected:** M1's point is to settle a format that content is then written against.
5. **Landing and the weaver stay out.** Studio → pull request → content repo is M4; routes are M2.
   M1 stops at *the graph is in Postgres and readable*.

## What is next — the M1 parts

In this order. Nothing can be validated before the format exists, no fixture written before the
links have a shape, and the API is last because it is the only part that cannot be checked without
the rest.

| # | Part | Objective | Check |
|---|---|---|---|
| 1 | The node folder and its core fields | `node.yaml` (id, title, claim, region, level) and `body.md` as opaque MyST; `code-schema` parses one node and writes it back | A node round-trips: files → objects → files, unchanged; a missing or malformed field names the file and the field |
| 2 | Links in the schema | *needs* groups (*all of* / *any of*, each with a reason), *goes deeper*, *related* — W3.2 as fields, including which file holds a peer link | A node with all three kinds round-trips; the peer cap and the group shape are refused with a message |
| 3 | Graph rules and the validate entry point | *needs* cycles, *goes deeper* cycles, links to nodes that do not exist; one command that validates a folder of nodes | Every rule has a failing test; a broken node is rejected with a message naming the file and the field |
| 4 | The Salmon fixtures | 8–12 real nodes in `tests/fixtures/`: both kinds of group, two levels, peers, a goes-deeper pair | The validator accepts them; they are the graph parts 5 and 6 read |
| 5 | The index and the loader | Django models for the index, filled from a folder of files — derived data, never edited | A rebuild from the fixtures gives the same index twice; a rebuild after an edit converges |
| 6 | Rebuild command and read API | `manage.py rebuild_index`; read-only endpoints for a node and its neighbours | The command rebuilds from files alone; `/api/nodes/<id>` returns the three kinds of link and the derived *needed by* |

M1 is done when R4's *done when* holds: the validator accepts the fixtures, rejects a broken node
with a message naming the file and the field, and the index rebuilds from the files alone. That is
the checks for parts 3, 4 and 6 together.

## Open questions

- **Which file holds a *related* link.** It shows on both pages but should be written once; part 1
  or 2 decides whether the index mirrors it or both files carry it.
- **Whether *goes deeper* must point one level further on** (T10.1), or may point within a level.
- **How ids are formed** — a slug the author chooses, or one derived from the folder name. It
  decides what a rename costs, and every link in the graph names an id.

## Traps

- **The format is the expensive thing to change.** Once fixtures and content are written against
  it, a field rename is a migration of files in another repository. Parts 1 and 2 are where to
  argue, and the arguing is cheap there.
- **`code-schema` is pure** (`tests/guards`): no Django, no HTTP client, no model library. The
  loader in part 5 lives in `apps/api`, not in the package.
- **Tests never read the real content repository** (R1). Everything in M1 runs against
  `tests/fixtures/`.
